# Snapshot Testing

This document describes the snapshot testing strategy for CosmosVote frontend components.

## Overview

Snapshot tests capture the rendered output of a component and store it as a reference. On subsequent test runs, the output is compared to the stored snapshot. If they differ, the test fails, alerting developers to unintended UI changes.

## Benefits

- **Regression detection**: Catch unintended UI changes
- **Documentation**: Snapshots serve as living documentation of component output
- **Confidence**: Ensure components render consistently across changes
- **Fast feedback**: Quick validation without manual visual inspection

## Running Snapshot Tests

### Run all tests
\`\`\`bash
cd frontend
npm run test
\`\`\`

### Run snapshot tests only
\`\`\`bash
npm run test -- --grep "snapshots?"
\`\`\`

### Update snapshots (after intentional UI changes)
\`\`\`bash
npm run test -- -u
# or
npm run test -- --update
\`\`\`

### Run specific component snapshot tests
\`\`\`bash
npm run test -- Header.snap.test.tsx
npm run test -- UserDashboard.snap.test.tsx
\`\`\`

## When to Update Snapshots

✅ **Safe to update:**
- Intentional UI/style changes
- New props or features added
- Refactoring that changes HTML structure
- Dependency updates that affect rendering

❌ **Review carefully:**
- Unexpected snapshot failures may indicate bugs
- Always review the diff before updating
- Consider if the change was intentional

## Snapshot Best Practices

### 1. Keep snapshots small and focused
Test one component state per snapshot:
\`\`\`typescript
it('matches snapshot when connected', () => {
  const { container } = render(<Header {...props} walletAddress="G..." />);
  expect(container).toMatchSnapshot();
});

it('matches snapshot when disconnected', () => {
  const { container } = render(<Header {...props} walletAddress={null} />);
  expect(container).toMatchSnapshot();
});
\`\`\`

### 2. Use meaningful test names
Test names should describe the component state:
- ✅ `"matches snapshot when connected with balance"`
- ❌ `"snapshot test 1"`

### 3. Mock dependencies
Use `vi.mock()` to isolate components:
\`\`\`typescript
vi.mock('../api', () => ({
  fetchDelegation: vi.fn(() => Promise.resolve(null)),
}));
\`\`\`

### 4. Test different states
Cover key variations:
- Loading states
- Error states
- Empty states
- Fully populated states
- Edge cases (very long text, etc.)

### 5. Review snapshot diffs
Before updating, always run:
\`\`\`bash
git diff frontend/src/components/__snapshots__/
\`\`\`

## Snapshot Storage

Snapshots are stored in `__snapshots__/` directories next to test files:

\`\`\`
frontend/src/components/
├── Header.tsx
├── Header.test.tsx
├── __snapshots__/
│   ├── Header.snap.test.tsx
│   └── Header.snap.test.tsx.snap    # Generated by vitest
├── UserDashboard.tsx
└── __snapshots__/
    ├── UserDashboard.snap.test.tsx
    └── UserDashboard.snap.test.tsx.snap
\`\`\`

**Important**: Snapshot files (`.snap`) must be committed to git!

## CI Integration

Snapshot tests run automatically in CI:
- PR builds fail if snapshots don't match
- Forces developers to review and commit updated snapshots
- Prevents unintended UI regressions from merging

See `.github/workflows/ci.yml` for the CI configuration.

## Troubleshooting

### Snapshots fail on CI but pass locally
- Ensure you've committed the `.snap` files
- Check for platform-specific differences (line endings, etc.)
- Run `npm run test -- -u` and commit the updated snapshots

### "Cannot find module" errors
- Verify all imports in test files are correct
- Check that mocked modules match actual module exports
- Run `npm install` to ensure dependencies are installed

### Large snapshot diffs
- Consider breaking the test into smaller, more focused tests
- Check if the component is too complex and should be split
- Use `toMatchInlineSnapshot()` for small, critical snapshots
